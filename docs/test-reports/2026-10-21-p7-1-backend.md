## 4. 可能問題(第一次執行的失敗;§2 第二次已證實修正有效)

**這是本分支引入的退步(基準 `825c0b0` 13/13 通過),且實際影響正式功能,不只是測試。**

- **根因(已確認)**:`ItAgentBack/src/stores/sql-monitor-store.ts:165`(`monitorTargets`,commit `99e94c2` D4/reboot_pending 加入)的子查詢使用 `d.boot_time`,但 `boot_time` 欄位在 **`ita.device_inventory`**(`db/migrations/0001_init.sql:50`),不在 `ita.device`。對 `_poc_test` 直接執行 `monitorTargets` 得到 `Invalid column name 'boot_time'`(SQL error 207)。
- **後果**:`AlertService.sweep()` 在 `monitorTargets` 丟錯時被外層 catch 吞掉並只記 warn(`alert-service.ts` sweep 的外層 try/catch),**整個自動類告警掃描(offline_long、disk_low、cert_expiring、clock_skew、agent_silent、agent_restarts)全部停擺**,不只 `reboot_pending`。若這版部署到測試區 / 正式區,告警會靜默失效。
- **為什麼單元測試沒抓到**:單元測試用記憶體假 store(`test/` 的 fake monitor store),不經 SQL;只有整合測試會執行真正的 SQL。
- 影響範圍:`monitorTargets` 的 `reboot_since` 欄位;`rebootRequiredSince` 判斷「晚於開機時間」需要改為 join / 子查詢取得 `ita.device_inventory` 的最新 `boot_time`(該表是否每台一列、是否只留最新一筆,需主工作階段確認)。
- 重現:`cd ItAgentBack && npx tsx --env-file=../../RustIt/ItAgentBack/.env --test test/int/*.int.test.ts`,看 P5(0006)那項。
